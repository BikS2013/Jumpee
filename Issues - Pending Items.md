# Issues - Pending Items

## Pending

1. **Jumpee - Launch at Login**: Jumpee does not auto-start on login. To add it, go to System Settings > General > Login Items and add Jumpee.app manually, or implement a LaunchAgent plist.

2. **Jumpee - Private API Stability**: Jumpee uses private CoreGraphics APIs (CGSGetActiveSpace, CGSCopyManagedDisplaySpaces) which are not guaranteed to remain stable across macOS updates. If a future macOS update breaks space detection, the CGS API calls may need to be updated.

3. **Jumpee - Multi-display global position verification**: The multi-display feature assumes that the display order in CGSCopyManagedDisplaySpaces matches macOS's global Ctrl+N space numbering. This needs verification on actual multi-display hardware. If the ordering doesn't match, navigation to spaces on non-primary displays may go to the wrong space.

4. **Jumpee - Multi-display UUID format verification**: The display ID mapping uses CGDisplayCreateUUIDFromDisplayID to match CGS display identifiers to NSScreen instances. The case-insensitive UUID comparison should handle format variations, but needs testing on various display configurations (HDMI, DisplayPort, USB-C, AirPlay).

5. **Swift Command Line Tools - Stale modulemap**: The file `/Library/Developer/CommandLineTools/usr/include/swift/module.modulemap` was renamed to `.bak` to fix a SwiftBridging module redefinition error. This may need to be re-applied after Command Line Tools updates.

6. **Jumpee - Overlay per space**: The overlay currently shows a single name (current space) on all desktops. Ideally each space would show its own name in Mission Control thumbnails, but the `CGSMoveWindowToSpace` private API is not available on the current macOS version.

7. **Jumpee - Navigation limited to 9 desktops per display; cross-display navigation broken on macOS 27**: The popover and menu offer Cmd+1..9 per display. Within the active display navigation uses Ctrl+Left/Right steps (v1.9.4); a desktop on another display still uses the global Ctrl+1..9 shortcut, which macOS 27 ignores when synthesized, so cross-display navigation does not work there.


9. **Jumpee - Move Window: macOS 15+ forces follow-window behavior**: On macOS 15 (Sequoia) and later, all approaches to moving a window between spaces force the user to follow the window. "Move without following" is impossible. This is a platform limitation, not a Jumpee limitation. Documented in plan-004.

10. **Jumpee - Move Window Hotkey Cmd+M conflicts with system Minimize**: The default move-window hotkey (Cmd+M) conflicts with the system-wide "Minimize" shortcut used by most macOS apps. When Jumpee registers this hotkey, Cmd+M triggers Jumpee's popup instead of minimizing. Users should change to an alternative (e.g., Cmd+Shift+M) via the Hotkey Configuration UI or config file. Documented in technical-design-v1.3.0-hotkey-about.md.

11. **Jumpee - Config default exception for moveWindowHotkey**: The `moveWindowHotkey` config property defaults to Cmd+M when absent and `moveWindow.enabled` is true. This is a documented exception to the project's "no default fallback for config settings" rule. The exception is centralized in the `effectiveMoveWindowHotkey` computed property. Must be recorded in the project's memory file before v1.3.0 implementation begins.

12. **Jumpee - Config default exception for pinWindowHotkey**: The `pinWindowHotkey` config property defaults to Ctrl+Cmd+P when absent and `pinWindow.enabled` is true. This is a documented exception to the project's "no default fallback for config settings" rule, identical to the `moveWindowHotkey` exception (item 11). The exception is centralized in the `effectivePinWindowHotkey` computed property.

13. **Jumpee - Pin Window: CGSSetWindowLevel cross-app reliability unverified**: The `CGSSetWindowLevel` private API is used to elevate other apps' window levels. While the API compiles and the build succeeds, actual cross-app pinning behavior has not been verified at runtime. If macOS resets window levels on focus change, a periodic re-assertion timer may be needed (see project-design.md, Section 16 Risks).

16. **Jumpee - Config default exception for InputSourceIndicatorConfig appearance properties**: The `InputSourceIndicatorConfig` struct uses documented default values for appearance properties (fontSize: 60, fontName: "Helvetica Neue", fontWeight: "bold", textColor: "#FFFFFF", opacity: 0.8, backgroundColor: "#000000", backgroundOpacity: 0.3, backgroundCornerRadius: 10, verticalOffset: 0) when the corresponding JSON keys are absent. This is a documented exception to the project's "no default fallback for config settings" rule, following the same pattern as `moveWindowHotkey` (item 11) and `pinWindowHotkey` (item 11). The defaults are centralized in static constants on `InputSourceIndicatorConfig` and exposed via `effective*` computed properties.

17. **Jumpee - Config default exception for `dropdownAtCursor`**: The `dropdownAtCursor` config property defaults to `true` when absent. When `true`, pressing the dropdown hotkey pops the menu at the current cursor location; when `false`, it falls back to opening at the menu-bar item (the original behavior). The default is centralized in the `effectiveDropdownAtCursor` computed property on `JumpeeConfig`. This is a documented exception to the project's "no default fallback for config settings" rule, following the same pattern as items 11, 12, and 16.

18. **Jumpee - Config default exception for `menuBarVisible`**: The `menuBarVisible` config property defaults to `true` when absent. When `true`, the menu-bar status item is shown (original behavior); when `false`, the status item is hidden via `NSStatusItem.isVisible` while global hotkeys remain active — pressing the dropdown hotkey still opens the menu (forced into cursor-popup mode in that case, since `performClick` on a hidden button is a no-op). The default is centralized in the `effectiveMenuBarVisible` computed property on `JumpeeConfig`. This is a documented exception to the project's "no default fallback for config settings" rule, following the same pattern as items 11, 12, 16, and 17.

19. **Jumpee - "Switch to Desktop N" (Ctrl+1..9) can go dead until the Dock restarts; direct jumps are possible again** (found 2026-09-23): on this Mac (macOS 27.0) Ctrl+1..9 did not switch desktops even when typed on the real keyboard, although symbolic hotkeys 118-126 were enabled and mapped to Ctrl+1..9 and a listen-only event tap showed the key arriving with only Control held (code 20, flags 0x40101); Ctrl+Left/Right typed or synthesized did switch. After `killall Dock`, both typed and synthesized Ctrl+N jumped directly to the desktop in about 0.2 s (6 -> 9 and back), without passing through the desktops in between. So the v1.9.2 conclusion that macOS 27 ignores synthesized Ctrl+1..9 most likely described this stale Dock state, not a platform rule. What makes the Dock go stale is unknown (this Mac has reordered desktops: space IDs 12, 13, 11 out of creation order). Proposed follow-up: navigation tries Ctrl+N first and, if the active space has not changed within about 0.6 s, falls back to the target-driven Ctrl+Left/Right steering in `SpaceNavigator.pressSpaceArrow`, which re-reads the active space before every press, so a late direct jump cannot cause an overshoot. Could also apply to Move Window (Ctrl+N while holding the title bar). Mitigation shipped in v1.9.6: the popover's hint line teaches ⌃1–⌃9 and a Reset Dock button in its footer restarts the Dock.

## Completed

0. **Jumpee - Pressing ⌃N with the popover open bounced back** (resolved 2026-09-23, v1.9.6, Sources/WorkspacePopover.swift, `WorkspacePopoverController.popoverDidClose`): found while testing the new ⌃N hint. With the popover open, ⌃3 switched desktops (6 -> 7) and 0.5 s later returned (7 -> 6): the switch closed the transient popover, `popoverDidClose` re-activated the previously active app, and macOS followed it back to its desktop. Fix: `show(...)` records the active space; on close the previous app is re-activated only if that space is still active, checked on close and again 0.3 s later (the switch can close the popover before the new space registers). Verified: ⌃3 with the popover open stays on the new desktop; Escape still returns focus to TextEdit.

0. **Jumpee - Switching or moving a window across several desktops overshot the target** (resolved 2026-09-23, v1.9.5, Sources/main.swift, `SpaceNavigator.pressSpaceArrow(route:logTag:completion:)`, `MenuBarController.desktopRoute(toGlobalPosition:)`, `SpaceDetector.allSpaceIDsInOrder(onDisplay:)`): after v1.9.4, choosing a desktop often landed one or more desktops further. Root cause: v1.9.4 counted presses and re-sent a press that had not changed the active space within 1 s. Measured on this Mac, a synthesized Ctrl+Right registers in `CGSGetActiveSpace` 0.55-0.6 s after the press, so under load or while dragging a window a slow switch was taken for a dropped press; the re-sent press then switched one desktop too many. Fix: the loop is now target-driven. `desktopRoute` returns the display's full left-to-right space order (full-screen app spaces included, since Ctrl+Left/Right steps through them too) and the target space ID. Before each press the active space is read, the loop stops at the target, and otherwise presses towards it, waiting up to 2.5 s for the change and 200 ms to settle; at most 2 x steps + 3 presses. A late switch can no longer overshoot, and any overshoot is corrected by the next press. Verified end to end through the installed app, idle and with every CPU core saturated: popover navigation 2 -> 6 and Move Window 2 -> 6 -> 2 passed through each desktop exactly once and stopped on the target.

0. **Jumpee - Move Window stopped part-way on multi-desktop moves** (resolved 2026-09-23, v1.9.4, Sources/main.swift, `SpaceNavigator.pressSpaceArrow(steps:logTag:completion:)`, `WindowMover.moveWindow(byDesktops:targetApp:)`): moving a window several desktops carried it only some of the way. Root cause: while holding the window, the mover sent Ctrl+Left/Right at a fixed 450 ms interval, and macOS drops a press that arrives while the previous switch animation is still running. Reproduced with `test_scripts/test-window-move-live.swift --app TextEdit --dest 4`: 4 presses, the window travelled 3 desktops (space 6 -> 9 instead of 10). Fix: the new closed-loop `pressSpaceArrow` waits after each press until `CGSGetActiveSpace` reports a change, lets it settle for 200 ms, then sends the next press, re-sending a press that has not switched within 1 s (up to 3 attempts per step). The mover and desktop navigation both use it. Verified with the test script's new `--closed-loop` mode (four 4-desktop moves, all exact) and end to end through the installed app (Cmd+J, Cmd+M, Desktop 6 from Desktop 2 and back: both landed with the window).

0. **Jumpee - Choosing a desktop beeped and did not switch on macOS 27** (resolved 2026-09-23, v1.9.4, Sources/main.swift, `SpaceNavigator.navigate(bySteps:)`, `MenuBarController.switchToSpace(globalPosition:)`): after v1.9.3, choosing a desktop in the popover played the system alert sound and nothing happened. Root cause: navigation synthesized "Switch to Desktop N" (Ctrl+1..9), which the macOS 27 system hotkey layer ignores (re-verified 2026-09-23 with `CGSGetActiveSpace` before and after a synthesized Ctrl+2: no change, while a synthesized Ctrl+Right switched). The unconsumed keystroke went to the active app; in v1.9.2 that was the re-activated previous app, and after the v1.9.3 change it was Jumpee, which has no key window and beeped. Fix: `switchToSpace(globalPosition:)` converts the chosen desktop into a signed step count on the active display (`desktopSteps(toGlobalPosition:)`) and `SpaceNavigator.navigate(bySteps:)` presses the Mission Control "Move left/right a space" shortcut (symbolic hotkeys 79/81, read with `CGSGetSymbolicHotKeyValue`) once per desktop, waiting for each switch (see the Move Window entry above); Ctrl+N remains only for a desktop on another display. Verified end to end through the installed app: Cmd+J then Cmd+3 moved from desktop 2 to desktop 3 and stayed there, Cmd+J then Cmd+2 returned.

0. **Jumpee - Switching desktop from the workspace popover bounced back to the focused window's desktop** (resolved 2026-09-23, v1.9.3, Sources/WorkspacePopover.swift, `WorkspacePopoverController.init`, `onNavigate`): with a window focused, picking another desktop in the popover switched desktops and then immediately returned to the original one. Root cause: `onNavigate` closed the popover with `restoreFocus: true`, so `popoverDidClose` called `previousApplication.activate()`; activating an app whose window lives on the old desktop makes macOS switch back to that desktop, undoing the Ctrl+N switch. Fix: `onNavigate` restores focus only when the chosen desktop is the current one; for a real switch Jumpee does not re-activate the previous app, so the new desktop stays and macOS focuses its own frontmost window.

5. **Jumpee - Hide/Show Menu Bar Icon toggle title did not refresh after hiding** (Sources/main.swift, rebuildSpaceItems, line 1828): After clicking "Hide Menu Bar Icon", reopening the dropdown via the hotkey still showed the stale "Hide Menu Bar Icon" label instead of "Show Menu Bar Icon", leaving the user no obvious way to bring the icon back. 6. **Jumpee - Move Window hotkey did not show popup until app gained focus** (Sources/main.swift, openMoveWindowMenu, line 1544): Pressing the move-window hotkey from another app did nothing; the popup surfaced later when the user clicked a window, and queued presses surfaced sequentially after each ESC. 21. **Jumpee - Move Window did nothing on macOS 27** (resolved 2026-09-16, v1.9.2): Choosing a destination from the Move Window menu (popover button or global shortcut) had no visible effect and logged nothing. Root cause: `WindowMover.moveToSpace()` located the window to move by asking the system-wide Accessibility element for `kAXFocusedApplicationAttribute`, and on macOS 27.0 (build 26A428) that query returns `kAXErrorCannotComplete` (-25204) even for a process that is trusted for Accessibility, so the mover returned silently before simulating the drag. `WindowPinner.getFocusedAppAndWindow()` used the same query and was affected in the same way. Fix: the new `FocusedWindowResolver` asks the target application's own element (`AXUIElementCreateApplication(pid)`) for its focused window, trying the app the user was working in first, the system-wide focus second, and the frontmost application third; both the mover and the pinner use it. The workspace popover now records the application that was frontmost before it opened and passes it through `openMoveWindowMenu(targetApp:)` and the menu items' `representedObject` to `moveToSpace(index:targetApp:)`, so the move targets the user's window even when Jumpee itself is still frontmost after the popover closed. Every bail-out point in the move path now prints a `[Jumpee:Move]` / `[Jumpee:Focus]` diagnostic. A second defect surfaced on the popover path once the first was fixed: the destination menu closed by itself before a desktop could be chosen. The popover closed with `restoreFocus: true`, so `popoverDidClose` re-activated the user's app after the popover's dismissal animation, and that app switch landed while Jumpee's pop-up `NSMenu` was open and dismissed it. Fix: the Move Window handler now closes the popover with `restoreFocus: false`, runs the move handler from `popoverDidClose` (new `afterCloseAction`, replacing the fixed 0.16 s timer), and `openMoveWindowMenu(targetApp:)` restores focus to the recorded app itself once the menu has closed, including on its early exits. A third defect remained once the menu stayed open: choosing a destination still moved nothing. The drag routine fired the "Switch to Desktop N" shortcut (Ctrl+N) while holding the window, and on macOS 27.0 synthesized Ctrl+1..9 presses are ignored by the system hotkey layer (verified from a standalone process with every event source and tap location, and with AppleScript `key code`, while the same keystrokes typed into TextEdit arrive and synthesized Ctrl+Left / Ctrl+Right do switch desktops). Fix: `WindowMover.moveWindow(byDesktops:targetApp:)` now presses the Mission Control "Move left/right a space" shortcut (symbolic hotkeys 79 / 81) once per desktop, 450 ms apart, while the title bar is held, and `MenuBarController.desktopSteps(toGlobalPosition:)` converts the chosen desktop into a signed step count on the active display. Verified live with `test_scripts/test-window-move-live.swift` (one and two steps) and end to end through the installed app: Ctrl+Cmd+M on a TextEdit window, choose a destination, the window and the desktop both arrive. The Settings "Mission Control Shortcuts" status now requires both Ctrl+1 and Ctrl+Left/Right to be enabled; README and the functions registry list the new prerequisite. Verified with `test_scripts/test-window-mover-diagnostics.swift`: the system-wide query fails, the per-application query resolves the frontmost app's window, position and minimize button, and the symbolic hotkeys 118-126 resolve to Ctrl+1..9 as enabled.
